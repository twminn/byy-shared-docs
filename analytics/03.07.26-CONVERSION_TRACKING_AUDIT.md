# Conversion Tracking Audit — March 2026

## Summary

An audit of GA4 conversion tracking across all BYY properties found that **purchase events are firing correctly on bestyearyet.io, but cross-domain attribution is broken**. Conversions from paid campaigns (Meta Audience Network, Facebook Ads) are being misattributed to `(direct)/(none)` because GA4 loses the session when users redirect from landing pages to the Rails app.

## Root Cause: Broken Cross-Domain Session

```
User Journey (current — broken):

1. User clicks Meta/Facebook ad
   → Lands on new.bestyearyet.com?utm_source=an&utm_medium=paid
   → GA4 session starts, attributed to an/paid ✅

2. User clicks "Subscribe Now" CTA
   → handleSignup() redirects to bestyearyet.io/signup?plan=yearly&source=landing_new
   → ❌ UTM params NOT forwarded
   → ❌ No cross-domain linker parameter (_gl)
   → GA4 starts NEW session on bestyearyet.io, attributed to (direct)

3. User completes Stripe checkout → purchase event fires
   → GA4 records purchase under (direct)/(none) ❌
   → Should be attributed to an/paid ✅
```

## Issues Found

### 1. No Cross-Domain Tracking Configured
GA4 does not have cross-domain measurement configured between:
- `bestyearyet.com` (main site)
- `new.bestyearyet.com` (landing page)
- `gift.bestyearyet.com` (landing page)
- `bestyearyet.io` (Rails app — where purchases happen)

Without this, GA4 treats each domain as a separate site and starts a new session on redirect.

### 2. UTM Parameters Lost on Redirect
Landing page CTAs redirect to `bestyearyet.io` without forwarding UTM parameters:

```javascript
// sites/new/script.js — handleSignup()
const signupUrl = new URL('https://bestyearyet.io/signup');
signupUrl.searchParams.set('plan', plan);
signupUrl.searchParams.set('source', 'landing_new');  // Custom param, not utm_source
signupUrl.searchParams.set('promo', 'newyear2026');
// ❌ Original UTM params (utm_source, utm_medium, utm_campaign) are NOT forwarded
```

### 3. `sign_up` Event Not Fired
`BYYAnalytics.trackSignup()` exists in the Rails app but is never called. New user registrations are not tracked as events.

### 4. `initiate_checkout` Not Fired
`BYYAnalytics.trackInitiateCheckout()` exists but is never called when users start the Stripe checkout flow.

## Two Distinct Conversion Events

We track two separate conversion events, each marked as a Key Event in GA4:

| Event | GA4 Event Name | When Fired | Business Meaning |
|-------|---------------|------------|------------------|
| **Registration** | `sign_up` | User provides email/phone and completes verification | We captured their contact info — a lead is created |
| **Purchase** | `purchase` | User completes Stripe checkout for a subscription | Revenue-generating conversion |

Both events should appear as **separate columns** in all dashboard tables and reports (not lumped into a single "Conversions" count). The dashboard now shows "Registrations" and "Purchases" columns throughout.

Future conversion events (e.g., `newsletter_signup`) can be added to the `CONVERSION_EVENTS` list in `src/dashboard/data_service.py` when ready.

## Expected Outcome

After implementing these changes:
- `sign_up` events will fire on every new registration, attributed to the traffic source that brought the user
- `purchase` events on `bestyearyet.io` will be attributed to the original traffic source (Meta ads, Google, etc.)
- The marketing dashboard will show separate Registration and Purchase counts per campaign and landing page
- First-touch and last-touch attribution models will be supported at the macro level
